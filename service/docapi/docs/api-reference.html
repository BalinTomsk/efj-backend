How responses are shaped

ApiResponse<T>

Every docapi response — success or failure, from any of the seven controllers — is wrapped the same way, so a caller never has to branch on shape before it can check for an error.

Envelope fields

  • datathe payload on success. null on error.
  • error{ code, message } on failure, null on success. Codes: not_found (404), invalid_document (400), internal_error (500).
  • metaalways present — currently just a response timestamp.

The shared document CRUD contract

AbstractDocumentController

News, Fish, Waterbody and Station each inherit the same three verbs on their own base path — only the entity and its backing stored procedures differ. The request body is consumed as a raw JSON string, so the shape of a document is whatever that entity's stored procedure expects, not something validated at this layer.

CallBehaviour
GET/<entity>/{id}Returns the stored document as real nested JSON. Unknown id → 404 not_found.
POST/<entity>Inserts a new document. 201, body { "id": <newId> }. Blank/malformed JSON → 400 invalid_document.
PUT/<entity>/{id}Updates an existing document. 200, body { "id": <id> } (falls back to the supplied id if the update returns no scalar).
  • Only news is backed by real SQL objects today. waterbody, fish, and station route correctly but their fn_<entity>_doc / sp_<entity>_doc_add / sp_<entity>_doc_update functions were never created in envfish-db — every call 500s with the standard error envelope (no stack trace or SQL leaks). Once created, the expected status for a missing id becomes 404, same as News.
  • Writes are shown for completeness but are not exercised against production here — see Access below for why.

News

NewsController · /api/v1/news

The one entity with a fully-built backend: the generic CRUD above, plus five endpoints for the News-page UI and JSON import/export.

Backing (2026-08-31): GET /{id}, /news/list, and /news/default below now read from the MySQL news table (Winhost — the same table News.aspx reads) instead of SQL Server; the JSON field names are unchanged. (2026‑09‑12, docapi 1.10.0) /news/search moved to MySQL too, and gained fish/country/offset/limit — see that endpoint below. (2026‑09‑14, docapi 1.11.0/1.12.0) /news/lake/{guid} and /news/fish/{guid} were added on the same MySQL backing, for the portal’s water-body and species pages. (2026‑09‑17) /news/export/{id} moved to MySQL as well, against the new sp_news_doc_export — a field-for-field port of dbo.fn_news_json. It had been quietly dead since 2026‑09‑14, when AddNews.aspx’s writes moved to MySQL: every article published after that date had no SQL Server row for the export to find. (2026‑09‑18, docapi 1.16.0) The writes followed: POST, PUT /{id} and /news/import now write the MySQL news table too (see “News writes” below), so every endpoint in this section is MySQL-backed and docapi no longer touches SQL Server’s dbo.news at all. (2026‑09‑03) /news/default is a pure MySQL read too: the SQL Server lookup that turned the mentioned lake_id/fish*_id into names (dbo.fn_news_ref_names_json, docapi 1.8.0‑1.8.1) was removed, because it made one news read span both databases. Every news read here now emits bare guids and leaves the names to the caller.

News writes (docapi 1.16.0). POST /api/v1/news, PUT /api/v1/news/{id} and POST /api/v1/news/import go to MySQL (sp_news_doc_insert / sp_news_doc_update) and share one validator. News is the one entity here with a schema, so unlike the generic CRUD above:

  • Body shape. POST/PUT take the snake_case document GET /{id} returns: title (required), author, author_link, source, source_link, video_link, paragraph0–2, country, date (yyyy-MM-dd), lake_id, credit, photo_alt, base64 photo, and species as fishes:[{"id":…}] or fish1_id–fish3_id. A GET body can be edited and PUT straight back — its line-wrapped base64 photo and fishN_id fields are accepted as they come.
  • 400 before any database call for a non-object body, a blank title, a field longer than its column (e.g. title 128, credit 64 characters), a country that is not two letters, or photo data that is not base64. (Under SQL Server a missing title came back as a 500.) A lake_id/fish id that is not a GUID is dropped, and an unparseable date is ignored, as before.
  • PUT is a full replace — a field left out is cleared — except that a missing date keeps the stored date, a missing photo keeps the stored photo, and whether the article is published never changes. An unknown id is a 404 and writes nothing (under SQL Server it answered 200 having changed nothing).
  • POST and import always create a published article. Every write clears docapi’s news caches, so it shows on the next read.

CACHING — CHANGED 2026‑09‑17. Every GET on this controller is now served from an in-process cache, and the database is read only when the entry answering the request is empty. Five endpoints (/news/export/{id}, /news/search, /news/lake/{guid}, /news/fish/{guid}, /news/photo/{id}) read through on every request until this change and each gained a 25-entry LRU. The reason is the cost of a miss rather than the size of the key space: the MySQL pool keeps no idle connection (minimumIdle=0, idleTimeout=15s), so a read on a quiet minute pays a full TCP connect and authentication to Winhost over the public internet before the query starts — /news/export/{id} measured ~2 s per call through the gateway. Every entry is dropped by one clear a day at 00:00 UTC, which is deferred while the database is unreachable so an outage leaves stale content serving rather than an unfillable empty cache. Nothing else expires, with one exception: GET /news/{id} remembers an unknown id for 60 s so a newly published article still appears within a minute.

Two consequences worth knowing. (1) An unknown id is never cached by NewsQueryCache — only GET /news/{id} remembers misses — so a 404 from /news/export/{id} or /news/photo/{id} always cost a database round trip and always will. (2) When you are verifying a deploy, time the first call, not the second: a repeat of the same id now answers from memory in milliseconds and proves nothing about the database path. Use a different id for a second sample.

GET/api/v1/news/list?country=&offset=&limit=
paged latest news · order by role
ParameterRequiredNotes
countryOptionalISO-2 code. Blank/absent = all countries. A thin non-CA country (< 100 items) is padded with CA news up to 100. Malformed → 400.
offsetOptionalRows to skip; negative/absent → 0.
limitOptionalPage size; default 25, capped at 200.
X-Fish-Role (header)Set by cproxyguest / user / admin, stamped by cproxy 0.17.1 from the verified credential. Not a parameter you send — cproxy overwrites any copy a caller supplies. Missing or unrecognised → guest (fails closed).

Order and window depend on the caller's role (docapi 1.18.1). admin — most recently edited article first (whole list, paged). user — newest article date first (whole list, paged). guest — newest article date first, and only the first 100 rows are ever reachable: offset+limit is clamped to 100 and total never exceeds 100, so a pager built from it never offers an empty page; a window starting at or past row 100 answers an empty items. Ties break on the row id, so a pager never repeats or skips a row. Country is still the caller's: docapi never sees the visitor's address, so the IP→country lookup stays in News.aspx and docapi enforces only the window. An article an admin has just saved is on top of the next admin list, because every write stamps edit_stamp and clears the news caches.

Cached, and not as whole responses for the two big countries: US and CA are held as 100-row buckets, so one fetch answers every offset/limit window inside them — which is the natural unit, since fn_news_list already works in hundreds (it pads a thin non-CA country with CA news up to 100). Every other request — all-countries, another country, or a US/CA page reaching past its bucket — is cached as a whole response in a separate LRU of 100, keyed country|offset|limit. That last case was a genuine hole until 2026‑09‑02: a deep page re-queried on every request, so anything walking the pager hit the database each time.

GET/api/v1/news/default
assembled home page

The Default.aspx home page's item set, in display order — the 2 lead articles first (with_photo: true, each carrying its base64 photo), then the 3 right-column picks. Each item is the full per-article document, so one call renders the whole page: headline, byline (author + author_link), flag, source/source_link, photo credit and photo_alt, both paragraphs, the right column's one-line snippet, and the lake_id / fish1_id…fish3_id it mentions.

FIXED 2026‑09‑09 (docapi 1.8.3). This endpoint and its two siblings (/news/featured, /news/more) were returning 500 in production. Cause: sp_news_default() is just SELECT doc FROM v_news_default_doc …, and v_news_default_doc was never created in the live Winhost database — only its dependencies (v_news_default_grp1..5, _ranked, _top) were applied, so the call failed with Table 'mysql_111487_envfish.v_news_default_doc' doesn't exist. /news/list was unaffected because it uses v_news_list_rows, which does exist — that asymmetry is what identified it as a missing object rather than a connectivity fault. The view could not be created from here: the app's MySQL account (portos) has no CREATE VIEW/CREATE ROUTINE privilege. So docapi 1.8.3 inlines the view's body into MySqlNewsQueryRepository.DEFAULT_SQL, depending only on objects that exist. To restore the intended design, run envfish-db/mysql/FIX_missing_v_news_default_doc.sql in the Winhost panel and revert that constant to CALL sp_news_default().

Cached as one assembled page — a single entry, since there are no parameters to key on. /news/featured and /news/more are projections of this same entry, so all three endpoints together cost one database read.

Names are not resolved here (changed 2026-09-03). The MySQL database backing this read holds only the news table, so the water body and species an article mentions come back as bare guids — a caller that wants display names resolves them itself. docapi 1.8.0–1.8.1 did resolve them via a SQL Server lookup, but that made the news read span both databases, which is exactly what moving these reads to MySQL existed to avoid; the lookup and its database function were removed. This is a pure MySQL read again.

GET/api/v1/news/photo/{id}
one lead photo, raw bytes

DEPLOYED AND VERIFIED LIVE 2026‑09‑12 (docapi 1.9.0). Fetched a real published article’s photo directly against the droplet (525,222-byte PNG, correct ETag/Cache-Control; matching If-None-Match → 304, stale → 200 with fresh bytes; unknown id and a photo-less real id both → 404), then re-fetched the same photo through cproxy 0.14.0 (which gates /news/photo exactly like its three siblings) and confirmed the bytes are identical. The portal’s NewsPhoto.ashx was confirmed to genuinely use this path — a never-before-cached article’s photo, requested through the live site, produced a matching line in cproxy’s own access log.

One article's lead photo (news_photo0) as the raw image bytes that were uploaded — not JSON, not base64, no envelope. This is the by-URL form of the photo /news/featured already embeds, and it exists so a caller can render the home page without re-downloading a megabyte of photos it has already cached. The portal's NewsPhoto.ashx seeds its own cache from the embedded copy while rendering and falls back to this endpoint on a miss, which is why the same bytes are reachable two ways on purpose.

Content type is sniffed from the file's own magic bytes — image/jpeg, image/png, image/gif, image/webp, else application/octet-stream. The column holds whatever was uploaded and is mostly JPEG, so a fixed image/png (which the portal's old inline markup used) would have been wrong for most of the library.

Caching. The bytes for an id are immutable in practice — replacing an article's photo replaces the bytes but keeps the id — so the response carries Cache-Control: public, max-age=604800 (7 days) and an ETag of "<id>-<length>". The length is what makes a replaced photo self-correct: the tag changes, revalidation misses, and the new bytes are sent. If-None-Match is answered with 304 and no body.

Server-side caching (new 2026‑09‑17) — a different layer from the paragraph above, which governs the browser. docapi now keeps the last 25 photo blobs in memory, keyed by lower-cased id, so a request that gets past the browser’s max-age no longer means a BLOB fetch across the public internet. These are the heaviest entries any news cache holds (~0.5 MB apiece, so ~13 MB when full), and they are held anyway precisely because a caller only reaches this endpoint once its own cache has missed — the moment the slow path hurts most. A 404 (unknown, unpublished, or photo-less id) is not cached and still costs a round trip.

Read by primary key, and that is not negotiable. news_photo0 is a LONGBLOB and the live Winhost host hangs indefinitely on any query that references it while materializing more than one row. MySqlNewsQueryRepository.PHOTO_SQL is a single-row lookup by primary key with news_publish = 1 in the key predicate — never widen it to a scan, a join or an IN list. The publish filter also means a draft's photo is a 404 here exactly as its text is invisible everywhere else.

GET/api/v1/news/search?q=&fish=&country=&offset=&limit=
full-text-ish search

CHANGED 2026‑09‑12 (docapi 1.10.0). This endpoint now reads the MySQL news table (4,824 published articles) instead of SQL Server's dbo.fn_news_search (427), joining the other three news reads that moved on 2026‑08‑31. It also gained fish, country, offset and limit, and its response now carries offset/limit alongside total, so one call renders a numbered pager. That completeness is the point: with search on the MySQL side, every news read the portal's News.aspx makes is a gateway read.

ParameterRequiredNotes
qRequiredTrimmed, capped at 100 chars. Blank/missing → 400. % and _ match literally.
fishOptionalComma-separated species ids to match in the article's three species slots. Blanks and duplicates dropped, capped at 3. See the note below on why ids rather than names.
countryOptionalISO-2 code to restrict results to. Omitted/blank = all countries. Not a 2-letter code → 400.
offsetOptionalRows to skip. Null/negative → 0. A window at or past the 100-match cap answers empty.
limitOptionalPage size. Null/<1 → 25, capped at 200.

Matches the term against the headline, the source, the three paragraphs and the three photo alts. Up to 100 matches, newest first, paged by offset/limit; total is the full match count, itself capped at 100.

Species are matched by id, and the caller supplies them. fn_news_search joined dbo.fish and matched the term against common, Latin and synonym names, so walleye found an article tagged with walleye even when the headline never said so. The MySQL database behind this endpoint holds only the news table, so that half of the match is preserved by having the caller resolve the term to species ids against its own catalogue and pass them in fish. Nothing is lost, and the article rows still come only from news. It is the same rule /news/list and GET /news/{id} already follow — names are the caller's to resolve — and it is deliberate: a server-side name join here would make one news read span both databases, which is exactly what dbo.fn_news_ref_names_json did before it was removed on 2026‑09‑03.

Consequence for the response: fishes (names) comes back empty on this backing, and the new fishIds carries the article's own species tags for the caller to resolve.

Cached since 2026‑09‑17. The last 25 whole search pages, keyed query|sorted fish ids|country|offset|limit. The key space is open-ended, which is why this used to read through on every request; what makes a bounded LRU pay anyway is that real traffic is not uniform over it — News.aspx’s search box produces the same handful of terms repeatedly, and a numbered pager re-issues the identical query for every page the reader steps through. Two details of the key: each offset/limit window is its own entry (so paging fills several), and the term is not case-folded — q=Walleye and q=walleye are separate entries even though the LIKE behind them is case-insensitive, because the response echoes query back verbatim and folding them would change the body. The species ids are sorted, since nothing echoes them and the SQL ORs the three slots.

GET/api/v1/news/lake/{guid}?limit=
one water body’s news

NEW 2026‑09‑14, docapi 1.11.0 — DEPLOYED AND VERIFIED LIVE the same day (1.12.0 image, digest sha256:61c7c92c…c45d8e), including through cproxy. The news panel of the portal’s public water-body page (Resources/wfRiverViewer.aspx) read SQL Server’s dbo.fn_river_view_news directly. ParameterRequiredNotes
guidPathThe water body’s GUID, canonical 8-4-4-4-12 hex. Anything else → 400. Matched case-insensitively (the column’s collation is utf8mb4_unicode_ci), and lower-cased before the query.
limitOptionalHow many articles. Null/<1 → 12 — fn_river_view_news’s own TOP 12, so the panel is unchanged — capped at 200.

Published articles whose lake_id is this water body, newest first. Narrow by design: a headline, a source badge and a date are all that panel renders, so nothing else is selected.

No 404. A water body with no news answers 200 with an empty items. “This lake has no news” is an ordinary answer, not a missing document — unlike /news/{id}, where an unknown id genuinely is one.

One list, not two columns. fn_river_view_news takes a @col argument and returns every other row, because it was written to be called once per rendered column. That split is layout: this returns one ordered list and the caller deals it into columns. news_id is the tiebreaker after the timestamp so the order is total — two articles sharing a timestamp swapping places between requests would move a headline from one column to the other on a refresh.

Stricter than what it replaces: news_publish = 1 is part of the predicate. fn_river_view_news never checked the flag, so it could show a draft’s headline linking to an article the reader cannot open; its sibling fn_fish_view_news did check it.

Cached since 2026‑09‑17 — and safe to run per page view even on a miss. One entry per water body across tens of thousands of them, so a 25-entry LRU (keyed guid|limit) will never hold more than a sliver of that key space; it earns its place because page views are not spread evenly over it, and repeat/refresh traffic on a public page lands on the same few ids. Until this change NewsQueryCache passed this straight through on every request, which was affordable only because of how narrow the statement is: five short columns, no photo column referenced (not even has_photo0), no window function, so the plan never buffers rows while touching an off-page column. That is the rule the live Winhost host imposes, it still governs every miss, and it must not be widened.

  • Why that cache exists. This is the most expensive read the service makes — sp_news_doc_export base64-encodes three LONGBLOB photo columns into one JSON value, and the result is then parsed and re-serialized on the way out. Measured through the gateway on 2026‑09‑17 it took ~2 s per call, most of it the cold connection to Winhost (the pool keeps no idle connection). These are the largest values any news cache holds — the document verified live on 2026‑09‑17 was 512,506 bytes on the wire, and rather more in heap once parsed — so docapi.cache.news.export is the first knob to turn down if the container’s heap gets tight. GET/api/v1/fish?province=&codes=&country=
regional code → Latin name

Resolves the short codes provincial agencies use for fish species to a Latin binomial. dbo.fish_code is keyed on country + state + code, so a bare code has no meaning on its own — province is required the moment codes is supplied.

ParameterRequiredNotes
provinceRequired*Two-letter province/state code. *Required whenever codes is present.
codesOptionalCodes to resolve. Omit entirely to fetch every code in the province, ordered by code.
countryOptionalDefaults to any — only CA exists in the catalogue today, but country is part of the key.
  • One element per match, not per code. A code can legitimately name more than one species — BC RB is both Rock Bass and Rainbow Trout on the live catalogue. Picking a single "best" match would silently discard the other.
  • Order is preserved and a code with no match still occupies its slot — latin: null — rather than vanishing.
  • An unknown province is not an error — codes simply resolve to null.
  • Up to 100 codes per call — beyond that the whole request is refused with a 400.

How codes and fishes parse

Both lookups above share one parser. More than one value for a key means the parameter was repeated, and each is taken verbatim — the only way to pass an entry containing a comma without quoting it. Exactly one value is split on commas/semicolons, honouring quotes; one layer of {…}/[…] around the whole list is stripped first. This exists because roughly three in four names in the catalogue contain a comma of their own ("Bass, Guadalupe"), so a naive split on , alone would tear most of it in half.

?codes=BURB&codes=WALL → 2 entries, verbatim ?fishes="Bass, Guadalupe",Burbot → 2 entries, quote-aware split

RegulationController · /api/v1/river/regulation, /api/v1/region/regulation

Two of the three scopes Editor/LakeRegulation.aspx's single "regulation dialog" edits through one dbo.regulations table — water-body rules and region (country/state) rules; zone-scoped rules have no dedicated endpoint yet. There is no separate INSERT verb — every PATCH below upserts by identity: a body matching nothing existing inserts (action:"inserted"), one matching an existing row updates it in place (action:"updated"). This keeps the whole feature on cproxy's existing GET/PATCH-only allow-list, so it ships with no cproxy change. The identifying fields (lakeId, or country/state) always come from the URL, never the body — a caller can't accidentally write to a different scope than the route they called. A validation failure (missing year, an unknown lakeId/fishId, or zoneId+lakeId both set) is a 200 with an inline error, the same graceful contract as sp_lake_description_update's malformed-JSON path — not a 4xx.

Access & errors

cross-cutting
Public gateway: GET · POST · PATCH

docapi sits behind a reverse-proxy gateway whose method allow-list is GET,POST,PATCH. Every POST and PATCH — including the news writes and /news/import — needs a Bearer JWT carrying the day-key and a user claim; PUT (the generic document update) is refused at the gateway before it ever reaches docapi. (This card said “GET-only” until 2026‑09‑18; see the cproxy api-guide.html for the credential.)

PUT /api/v1/news/{id} → 405 {"error":{"code":"method_not_allowed", …}}
A different envelope on 405

That 405 comes from the gateway, not docapi, so it does not carry the { data, error, meta } shape — only { error: { code, message } }. Every response that actually reaches docapi uses the full envelope.

StatusWhenError code
200Request understood — including zero matches on a lookup, which is not an error.—
404Unknown document id, an unpublished news draft, or a path no controller (and no static resource) claims.not_found
400Missing/blank required parameter, malformed body, a value outside its accepted form (bad country code, batch over 100), or unreadable JSON.invalid_document
500The underlying SQL call failed — including "SQL object doesn't exist yet" for Waterbody/Fish-CRUD/Station. Never leaks a stack trace or SQL text.internal_error
405Gateway-level only — method not forwarded. docapi itself never returns this.gateway's own shape
