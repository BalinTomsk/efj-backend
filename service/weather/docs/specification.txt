GOAL
----
- Poll up to 900 US weather stations and up to 1400 non-US weather stations from MSSQL
  (dbo.vwWeatherForecastToDay).
- Fetch raw JSON latest-observation data from Weather.gov for US stations.
- Fetch raw JSON forecast data from Open-Meteo for CA stations.
- Store the raw JSON as-is into dbo.ows_meteo with source type 2. Do NOT parse JSON in Java.
- After each full pass, run post-processing stored procedures in order:
    1. dbo.spPushSpeciesFromLakeToStation
    2. dbo.spTotalUpdateProbability
    3. dbo.sp_clean_old_weather_data
- Log failures and skipped unpublished-source events; do not disable stations automatically.
- Sleep until next midnight between cycles.
- Expose a health endpoint on port 8081 for Docker/Kubernetes health checks.

STARTUP / CREDENTIAL LOADING
-----------------------------
Before Spring initialises:
1. Read DB_URL, DB_USERNAME, DB_PASSWORD from process environment or JVM system properties.
2. If any are missing, attempt to load from dotenv:
   - if DOTENV_PATH is set and non-blank → load that path
   - otherwise, if .env exists in the working directory → load it
   - ignore missing or malformed dotenv files
3. Collect dotenv values as a Map and register them via SpringApplication.setDefaultProperties()
   so secrets (especially DB_PASSWORD) are never written to the JVM-global System.setProperty()
   table where they would be visible to heap dumps and diagnostic tools.
   Real process env / JVM system properties always win (they take precedence over default properties).
4. The same dotenv fallback also covers SMTP_HOST, SMTP_PORT, SMTP_USERNAME, SMTP_PASSWORD,
   REPORT_EMAIL_TO, REPORT_EMAIL_FROM, and WEATHER_GOV_USER_AGENT -- all optional. Their
   absence is not a startup failure; see WEEKLY REPORT EMAIL and Weather.gov config below.

HEALTH ENDPOINT
---------------
Spring Boot Actuator serves on port 8081 — the application's ONLY HTTP listener
(server.port: 8081, no separate management port, nothing listens on 8080).
The app has no controllers, so this listener serves only the actuator endpoints;
every other path returns 404.

  GET /actuator/health           → overall status incl. DB indicator ({"status":"UP"})
  GET /actuator/health/liveness  → liveness probe (Docker HEALTHCHECK + k8s livenessProbe)
  GET /actuator/health/readiness → Kubernetes readiness probe

WORKER BEHAVIOUR
----------------
Thread
  Launched by StationWorker (ApplicationRunner).
  Thread names: weather-data-worker-open-us and weather-data-worker-open-ca.
  Non-daemon threads.
  If app starts with --console: do not launch background threads.
  Pauses (per-station pacing and between-cycle waits) go through a protected sleep(long ms)
  method so tests can subclass and run without real waits.

Graceful shutdown
  - A volatile `running` flag and each loop's interrupt check let workers stop cleanly.
  - @PreDestroy shutdown(): set running=false, interrupt each worker thread, join each up to 25s.
  - If a stop is requested mid-cycle the loop breaks and post-processing is SKIPPED.

Per-cycle loop
  1. Load stations for the worker country (US or CA) from dbo.vwWeatherForecastToDay
     (max 1400 per country).
  2. Compute target delay: max(8_hours_ms / stationCount, 2000). If count <= 1, use 2000 ms.
  3. For each station (unless stopping): process() → tally PROCESSED/SKIPPED/FAILED →
     sleep (targetDelay - actualProcessingTime). Skip sleep if negative.
  4. Post-processing gate (maybeRunPostProcessing):
       attempted = processed + failed   (skipped stations excluded)
       if attempted > 0 and failed/attempted > weather.worker.post-processing.max-failure-rate
         → log ERROR (cycle degraded) and SKIP post-processing
       else → run post-processing procedures
     Rationale: a high failure rate (e.g. open circuit / mass SQL failure) must not recompute
     probabilities from partial data; legitimate no-feed skips never block post-processing.
  5. Record a CycleReportEntry (date, worker, country, processed, failed, last processed/failed
     station) into CycleReportRecorder -- the same values as the "Worker cycle completed" log
     line. Only the background loop records; --console runs do not feed the recorder.
  6. Sleep until next local midnight (skip if already past boundary).


CONSOLE / DEBUG MODE (--console)
---------------------------------
Activated by --console command-line arg (@Order(0); exits process when done).
Optional: --station=<MLI> to filter to one station.
Runs exactly one processing pass; no background thread started.
Process termination goes through a protected exit(int) method (default System.exit) so tests
can exercise the console path without terminating the JVM.

StationWorker.runOnce returns a RunResult(processedStations, failedStations) record.
Exit code:
  1 → every attempted station failed (processedStations == 0 && failedStations > 0),
      so a cron/script wrapper can detect a fully broken pass
  0 → otherwise (a partial success still did useful work)


WEEKLY REPORT EMAIL (WeeklyReportMailService / CycleReportRecorder)
---------------------------------------------------------------------
Trigger: @Scheduled(cron = "${weather.report.cron:0 0 8 * * FRI}") -- every Friday at 08:00
  server-local time by default. Requires @EnableScheduling on WeatherStationPusherApplication.

Data source: CycleReportRecorder is an in-memory rolling buffer of the last 7 days per
  expected worker (14 total entries for Weather.gov/US and Open-Meteo/CA). CycleReportEntry
  records include date, worker, country, successfulStations, failedStations,
  lastProcessedStation, and lastFailedStation, appended once per completed background-loop
  cycle -- the exact same values as the "Worker cycle completed" log line.
  - NOT PERSISTED: a JVM restart (e.g. a mid-week deploy) clears the buffer, so a report
    generated right after a restart only covers cycles completed since then, not the full
    week. There is no DB table backing this.
  - --console runs do NOT feed the recorder -- only the production midnight loop does.

Skip conditions (logged, not an error, no email sent):
  - weather.report.to blank/unset → SMTP not configured for reporting.
  - BOTH CycleReportRecorder AND ServiceLifecycleTracker.recentIncidents() are empty.
    Incidents alone are enough to trigger a send -- a crash-loop that never completes a single
    cycle must not go unreported just because the cycle recorder is empty.

Send failure: caught (MailException), logged as an ERROR; never propagates out of the
  @Scheduled method.

From address: weather.report.from if set, else falls back to spring.mail.username, else
  omitted (mail server default).

Body: plain text (SimpleMailMessage):
  1. One line per recorded worker cycle:
     YYYY-MM-DD: worker=<provider> country=<country> processed=N failed=N
     lastProcessedStation=<mli|none> lastFailedStation=<mli|none>
  2. "Service reliability this week: " + either "no crashes or unexpected restarts detected."
     or "N crash(es) detected" followed by one line per incident:
     <detectedAt>: down from <downtimeStart> to <downtimeEnd> - <description>

SMTP itself is fully optional at the app level: spring.mail.host/port/username/password all
  default to blank (${SMTP_HOST:} etc.), so the weather worker starts and runs normally with
  no SMTP configured -- only the weekly email is skipped.


CRASH / UNCLEAN-RESTART TRACKING (ServiceLifecycleTracker / IncidentEntry)
---------------------------------------------------------------------------
Detection mechanism: a two-line marker file is written on every startup and rewritten on
  graceful shutdown:
    RUNNING|<startedAtIso>   -- written by @PostConstruct init()
    CLEAN|<shutdownAtIso>    -- written by @PreDestroy onShutdown(), fired when Spring
                                receives SIGTERM and has time to run its shutdown phase
  If the NEXT startup finds the marker still says RUNNING, the previous process never got
  that chance -- it crashed (OOM-killed, uncaught JVM error, kill -9, host reboot, or a
  forceful container removal that skips SIGTERM).

Incident description: the last ERROR/WARN line found by tailing the previous run's log file
  (weather.lifecycle.log-file, JSON-per-line via the existing Logstash encoder, parsed with
  the Jackson ObjectMapper already on the classpath via spring-boot-starter-web). Falls back
  to "no errors or warnings recorded before the restart" if the tail has none, or
  "no log data available" if the log file itself is missing/unreadable.

Downtime start: the timestamp of the last parseable line in that log tail (closer to the true
  crash moment than "when the crashed process started"); falls back to the marker's own
  startedAt, then to LocalDateTime.now().

CRITICAL DEPENDENCY: this only works if the deploy tooling stops the container gracefully
  (SIGTERM, e.g. "docker stop") instead of force-killing it. "docker rm -f" / "docker kill"
  sends SIGKILL immediately, skipping @PreDestroy -- every deploy would then be misreported
  as a crash. docs/do-update.md and the update-weather skill's Step 8 do
  "docker stop -t 30" (SIGTERM, wait) THEN "docker rm", so a normal deploy is NOT counted.

Persistence: state is a plain file under weather.lifecycle.state-dir (default
  /app/logs/.lifecycle, a subdirectory of the logs volume) -- not a database table. Nothing
  here fails startup: an unwritable/missing state dir is logged and skipped, same
  degrade-gracefully pattern as the SMTP-unconfigured case.

Retention: recentIncidents() returns and keeps only incidents detected within the last 7
  days, trimming the backing file (incidents.log) on read.


STATION QUERY (WeatherStationRepository)
-----------------------------------------
  SELECT TOP (?) mli, lat, lon, state
  FROM dbo.vwWeatherForecastToDay
  WHERE country = ?
  ORDER BY stamp DESC

StationWorker starts one pass loop for US and one for CA. US calls findSupportedUsStations()
with a 900-station limit for Weather.gov. Other countries call findSupportedStations(country)
with the default 1400-station limit.

Model: StationRef(String mli, double latitude, double longitude, String state)


HTTP FETCH (OpenMeteoFetcher)
------------------------------
Transport: HttpURLConnection, method GET. The connection is opened via
  URI.create(url).toURL().openConnection() (java.net.URL(String) is deprecated since
  Java 20 and must not be used directly).
Base URL: weather.worker.open-meteo-base-url (default https://api.open-meteo.com/v1/forecast).
  Overridable so tests can target a local server; production default is unchanged.
Connect timeout: weather.worker.connect-timeout-ms (default 15 000 ms).
Read timeout: weather.worker.read-timeout-ms (default 30 000 ms).
User-Agent: Chrome-like, e.g.
  "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.NN (KHTML, like Gecko) Chrome/124.0 Safari/537.NN"
  The two 537.NN WebKit/Safari build numbers are randomised in [11, 97]; seeded by the calendar
  day so they stay stable for a whole day and change from one day to the next
  (OpenMeteoFetcher.currentUserAgent).

Resilience (fetch is annotated @Retry + @CircuitBreaker + @RateLimiter, instance "openMeteo"):
  HTTP 200 → read response body as UTF-8 verbatim (no post-processing of the body), BUT:
             - body larger than weather.worker.max-response-bytes → IOException (retried)
             - body whose first non-whitespace char is not '{' → IOException (retried).
               This is a cheap shape guard, NOT JSON parsing: it keeps HTML error pages /
               captive portals out of ows_meteo; the accepted payload is still stored raw.
  HTTP 404 → throw FileNotFoundException (not retried; maps to SKIPPED upstream)
  HTTP 429 → honour Retry-After inline (delta-seconds or HTTP-date), clamped to
             [0, weather.worker.rate-limit.max-wait-ms]; retry up to rate-limit.max-retries.
             If still 429 → throw RateLimitedException (recorded by the breaker). The
             exception message reports the number of waits actually honoured (not one
             more than that — the wait counter is incremented only after the check and
             right before the wait, so "after N waits" means exactly N).
             Interrupt during the Retry-After wait → re-set interrupt flag and throw
             RateLimitedException (excluded from Resilience4j retry, so shutdown is not
             delayed by further backoff attempts).
  Other non-200 / timeout → throw IOException (retried with exponential backoff)
  Resilience4j AOP is active only on the Spring-managed bean at runtime (not in direct unit tests).

URL shape:
  https://api.open-meteo.com/v1/forecast
    ?latitude={lat}&longitude={lon}
    &hourly=temperature_2m,relative_humidity_2m,precipitation_probability,
            pressure_msl,wind_speed_10m,wind_direction_10m,weather_code,rain
    &daily=temperature_2m_max,temperature_2m_min
    &timezone=auto


HTTP FETCH (WeatherGovFetcher)
------------------------------
Transport: HttpURLConnection, method GET.
Base URL: weather.worker.weather-gov-base-url (default https://api.weather.gov).
Endpoint: /stations/{station.mli}/observations/latest.
Headers:
  User-Agent: weather.worker.weather-gov-user-agent. Weather.gov requires this; include contact info.
  Accept: application/geo+json.

Resilience (fetch is annotated @Retry + @CircuitBreaker + @RateLimiter, instance "weatherGov"):
  HTTP 200 -> read response body as UTF-8 verbatim, with the same max-response-bytes and
              first-non-whitespace-char-is-'{' guard used by OpenMeteoFetcher.
  HTTP 404 -> throw FileNotFoundException (not retried; maps to SKIPPED upstream).
  HTTP 429 -> honour Retry-After inline, clamped and bounded by weather.worker.rate-limit.
  Other non-200 / timeout -> throw IOException.

Weather.gov service-limit note:
  The official docs do not publish a daily request limit. They state rate limits are reasonable,
  not public, generous for typical use, and 429 responses may usually be retried after the limit
  clears, typically within about 5 seconds. The worker therefore spreads 900 US stations across
  the 8-hour budget (about 32 seconds per station) and still handles 429 Retry-After explicitly.


PERSISTENCE (WeatherDataRepository)
-------------------------------------
Save raw JSON:
  void saveStationData(String mli, String jsonData)
  - Reject blank mli → throw IllegalArgumentException
  - Blank/null jsonData → no-op
  - Runs in a transaction; @Retry(sqlRetry) + @CircuitBreaker(sqlBreaker)
  - If the UPDATE matches 0 rows (no ows_meteo row for that mli), log a WARNING
    with mli and payload size — the payload is dropped and must not vanish silently.
  SQL:
    UPDATE dbo.ows_meteo
    SET type = 2, ows = ?, stamp = GETDATE()
    WHERE mli = ?

  NOTE: this raw-table UPDATE is an intentional, grandfathered exception to the house
  rule that application code goes through a view/function/procedure rather than a raw
  table. It mirrors the legacy WeatherDataWorkerOpen .NET service exactly, and the rule
  only applies to methods added or changed going forward. If a save procedure for this
  table (e.g. spSaveStationWeather) is ever introduced, switch to it instead of writing
  a new raw-table statement elsewhere.

Post-processing procedures:
  pushSpeciesFromLakeToStation()  → EXEC dbo.spPushSpeciesFromLakeToStation
  totalUpdateProbability()        → EXEC dbo.spTotalUpdateProbability
  cleanOldWeatherData()           → EXEC dbo.sp_clean_old_weather_data
  Each runs in a transaction; each protected by Resilience4j retry + circuit breaker.
  Procedures may emit incidental result sets — drain with PreparedStatementCallback + getMoreResults.


PROCESSING PIPELINE
-------------------
StationProcessorBase (template method):
  process(StationRef) is final; calls processStation() inside try/catch and returns a
  ProcessingOutcome (PROCESSED / SKIPPED / FAILED) the worker uses for the post-processing gate:
    success              → PROCESSED
    FileNotFoundException → SKIPPED; log info "Skipping {country} station with no published {source}. ..."
    any other exception   → FAILED;  log warning "US station processing failed. station={mli} state={state}"

StationProcessorOpen:
  1. Fetch JSON from Open-Meteo using station lat/lon.
  2. Log save start with payload byte count.
  3. Update dbo.ows_meteo via WeatherDataRepository.
  4. Log station processed.

StationProcessorWeatherGov:
  1. Fetch latest-observation JSON from Weather.gov using station.mli as the station id.
  2. Log save start with payload byte count.
  3. Update dbo.ows_meteo via WeatherDataRepository.
  4. Log station processed.

StationPostProcessingService calls procedures in this exact order:
  1. dbo.spPushSpeciesFromLakeToStation
  2. dbo.spTotalUpdateProbability
  3. dbo.sp_clean_old_weather_data


TIMING MODEL
------------
  US: 900 stations, 8h budget → delay ≈ 28_800_000 / 900 = 32_000 ms per station
  CA: 1400 stations, 8h budget → delay ≈ 28_800_000 / 1400 = 20_571 ms per station
  Actual delay             → targetDelay − actualProcessingTime; never negative
  Between cycles           → sleep until next local midnight; skip if already past boundary


ERROR HANDLING
--------------
  Missing DB_URL / DB_USERNAME / DB_PASSWORD → Spring datasource fails at startup
  Blank mli during save                      → throw IllegalArgumentException
  Blank / null JSON payload                  → skip save
  HTTP 404 from Open-Meteo                   → FileNotFoundException; log skip; outcome SKIPPED
  HTTP 429 from Open-Meteo                   → honour Retry-After inline; if exhausted RateLimitedException → FAILED
  Interrupted during Retry-After wait        → RateLimitedException (no further retry); interrupt flag re-set
  200 body oversized or not a JSON object    → IOException; retried (backoff); if exhausted → FAILED
  UPDATE matches 0 ows_meteo rows            → log WARNING (payload dropped); still counts as PROCESSED
  HTTP non-200 other than 404 / timeout      → IOException; retried (backoff); if exhausted → FAILED
  Per-station processing exception           → log warning; outcome FAILED; continue
  SQL write failure                          → Resilience4j retry/circuit breaker; then propagates → FAILED
  Open Open-Meteo circuit                    → CallNotPermittedException fast-fail → FAILED
  High cycle failure rate (> max-failure-rate) → log ERROR; SKIP post-processing for the cycle
  Post-processing emits result sets          → drain with getMoreResults; continue normally
  Stop requested mid-cycle (@PreDestroy)     → break loop; skip post-processing; thread joins (<=25s)
  Worker thread interrupted                  → re-set interrupt flag; stop worker thread
  Unexpected worker loop exception           → log error; continue loop

Never: disable stations automatically; stop the worker for a single station failure; parse JSON.

DOCKER
------
Build stage  : maven:3.9.9-eclipse-temurin-21, runs mvn -B -DskipTests package
Runtime stage: eclipse-temurin:21-jre, copies jar to /app/weather-station-pusher.jar

Security:
  - Non-root user: groupadd appgroup (gid 1001) + useradd appuser (uid 1001, no home)
  - /app/logs created (mkdir -p) and chowned to appuser:appgroup so Logback file appender can write
  - jar is chowned to appuser:appgroup; USER appuser set before EXPOSE
  - ENTRYPOINT uses "exec java ..." so Java replaces the shell and receives SIGTERM as PID 1
  - curl installed in the runtime stage for HEALTHCHECK (eclipse-temurin:21-jre ships
    neither curl nor wget; a wget-based HEALTHCHECK would always report unhealthy)

  RUN apt-get update && \
      apt-get install -y --no-install-recommends curl && \
      rm -rf /var/lib/apt/lists/*
  EXPOSE 8081
  HEALTHCHECK --interval=30s --timeout=5s --start-period=60s --retries=3 \
    CMD curl -sf http://localhost:8081/actuator/health/liveness || exit 1
  ENTRYPOINT ["sh", "-c", "exec java $JAVA_OPTS -jar /app/weather-station-pusher.jar"]

The HEALTHCHECK targets /actuator/health/liveness, NOT the overall /actuator/health:
the overall endpoint includes the DataSource indicator, so a transient DB outage would
mark the container unhealthy even though the worker sleeps and recovers on its own.

.dockerignore must exclude: .git, .idea, target, docs, .env
Do NOT bake a real .env into the image.
